# ADIE Verifier

![ADIE v2.0.0](https://img.shields.io/badge/ADIE-v2.0.0-blue) ![Ed25519-signed](https://img.shields.io/badge/Ed25519-signed-green) ![offline](https://img.shields.io/badge/offline-no%20server-lightgrey)

**Verify formal decisions independently — in your browser, offline.**

Offline verifier for ADIE decision artifacts. Two independent verifiers,
two protocol versions. No installation. No network. No external dependencies.

---

## What is ADIE?

ADIE (Automated Decision Integrity Engine) produces formally verified,
cryptographically signed proofs for automated security decisions. Every
manifest you load here was generated by a formal SMT solver, hashed with
SHA-256, and signed with Ed25519. This page verifies those signatures
entirely in your browser — no server, no trust in this site is required.

## Try it

- **Live demo:** <https://Bashar100-A.github.io/adie-verifier/> (after gh-pages deploy)
- **Local:** `git clone https://github.com/Bashar100-A/adie-verifier && open index-v5.html`
- **One click:** on `index-v5.html`, press "Load all 3 manifests and verify" to check P12/P13/P14 together

## What you're verifying

Three claim classes are shipped as signed manifests:

- **P12** — 13 artifacts (evidence chain, canonicalization, signing)
- **P13** — 16 files (seccomp + Landlock sandboxing)
- **P14** — 32 files (TEE/AEP hardening, end-to-end)

Each manifest embeds the Ed25519 public key, SHA-256 hashes of every file,
RFC 8785 JCS canonical JSON, and one Ed25519 signature. Tamper with a
single byte and verification fails.

## v4 - Decision Certificates (RSA-2048, protocol v1.0)

Try it:
1. Open `index.html`
2. Drag `certificate-001.json` + `public-key-001.pem` -> expect `VALID`
3. Drag `certificate-001-TAMPERED.json` + `public-key-001.pem` -> expect `INVALID: E002_HASH_MISMATCH`

Standards: RFC 8785, RFC 6962, RSA-2048, SHA-256.

## v5 - ADIE v2.0.0 Manifests (Ed25519, manifest_version 1.0)

Try it:
1. Open `index-v5.html`
2. Drag `manifest-P12.json` -> expect `VALID`
3. Drag `manifest-P13.json` -> expect `VALID`
4. Drag `manifest-P14.json` -> expect `VALID`
5. Drag `manifest-P12-TAMPERED.json` -> expect `INVALID: PAYLOAD_HASH_MISMATCH`

Checks performed by v5:
1. **Structural validation** - manifest_version, claim_id, outcome, signature.* present
2. **Key identity pinning** - key_id == SHA256(SPKI DER)[:16]; must be in TRUSTED_KEY_IDS
   (default: 28f7e99132838f7a). Mitigates manifest-substitution attacks.
3. **RFC 8785 JCS canonicalization** - signature key excluded, keys ASCII-sorted
4. **SHA-256(canonical)** == signature.signed_payload_sha256
5. **Ed25519(signature.value, canonical, public_key_pem)** == valid

Error states: MALFORMED_JSON, UNSUPPORTED_MANIFEST_VERSION, MISSING_SIGNATURE,
UNSUPPORTED_ALG, KEY_ID_MISMATCH, UNTRUSTED_KEY, PAYLOAD_HASH_MISMATCH,
SIGNATURE_INVALID, CRYPTO_ERROR.

Standards: RFC 8785, RFC 8032 (Ed25519), SHA-256.

## Security regression tests

The following manifests verify two primary attack scenarios:

| File | Attack | Expected |
|---|---|---|
| `manifest-P12-TAMPERED.json` | Payload modified (outcome PASS->FAIL) | `INVALID: PAYLOAD_HASH_MISMATCH` |
| `manifest-P12-ATTACKER-KEY.json` | Manifest substitution (forged key, same payload) | `INVALID: UNTRUSTED_KEY` |

Both are rejected by v5. The pinning check (`TRUSTED_KEY_IDS`) fires
before hash and signature verification, so a correctly-signed manifest
from an unknown key is rejected outright.

## Technical details

- **Signature:** Ed25519 over a payload `{claim_id, outcome, files[], run_id, signed_at}`
- **Canonicalization:** RFC 8785 JCS (JSON Canonicalization Scheme)
- **Hash:** SHA-256 per artifact, embedded in `artifacts[]`
- **Public key:** embedded in `signature.public_key_pem` (self-verifying)
- **Key id:** short identifier in `signature.key_id` (dev / prod distinction)
- **Verification:** browser Web Crypto `crypto.subtle.verify('Ed25519', ...)`

## Security notes

Warning - Trust model: Both verifiers display dev_mode: true as a warning only.
Production deployments should replace dev keys with HSM/TEE-stored keys and
pin them out-of-band.

Warning - Key pinning: The v5 verifier rejects manifests whose key_id is not in
TRUSTED_KEY_IDS. Add new keys to that set only after explicit approval.

Warning - Browser support: Ed25519 in Web Crypto API requires Chrome 113+,
Firefox 130+, or Safari 17+. The v5 page checks this on load and displays a
clear error if unsupported (it does not silently fail).
